# spike-render: where Veky content gets rendered for free

Question A: can a branded flyer (1080x1350 and 1080x1920) render with Satori + resvg-wasm inside a Cloudflare Workers **free** plan?
Question B: how fast is an FFmpeg 9:16 reel on GitHub Actions (public repo) vs. local WSL, and what is the queue latency?

Everything here uses **synthetic inputs only** (generated by the scripts). No `samples/`, no `.env`, no secrets; the workflow has `contents: read` only.
Brand tokens come from `docs/00-vision-y-decisiones.md` section 13 (lila `#AC9FD6`, verde `#C3D787`, celeste `#A3D3DD`, Poppins). The logo does not exist yet: a "Veky" text wordmark is the placeholder. Poppins TTFs come from the `@expo-google-fonts/poppins` npm package (OFL-1.1) at install time; no font binaries are committed.

## Run it

```sh
cd spikes/render
npm ci
npm run check            # tsc --noEmit
npm run flyer            # CPU benchmark (Node), writes out/flyer-*.png
npm run bundle           # wrangler deploy --dry-run --outdir out/bundle (no login, no deploy)
npm run assets           # synthetic stills + clip -> out/assets
npm run reel             # renders out/reel.mp4 and validates it with ffprobe
```

Needs Node 20+ and `ffmpeg`/`ffprobe` (with libx264, drawtext, xfade). Set `WRANGLER_SEND_METRICS=false` to silence wrangler telemetry.
CI: `.github/workflows/render-spike.yml` (`workflow_dispatch`, or push touching `spikes/render/**`) installs ffmpeg, renders the reel, uploads `reel.mp4` as an artifact and prints timings.

## Results

### A. Flyer (Satori + resvg-wasm)

| Metric | Result |
|---|---|
| Free-plan CPU limit | **10 ms** per HTTP request ([limits](https://developers.cloudflare.com/workers/platform/limits/)) |
| Cold CPU, 1080x1350 (first render, includes satori/resvg init) | ~330 ms (Node, 1 run per invocation; range 330-350 ms across runs) |
| Cold CPU, 1080x1920 (second size, init already done) | ~175-185 ms |
| Warm CPU, 1080x1350 (median of 20) | ~145-175 ms (min 128 ms) |
| Warm CPU, 1080x1920 (median of 20) | ~180-190 ms (min 165 ms) |
| Loading wasm + fonts and compiling wasm | ~20 ms CPU |
| Bundle (`wrangler deploy --dry-run`) | Total Upload 4744.61 KiB (~4.6 MiB) uncompressed, gzip 1730.45 KiB (~1.7 MiB) |
| Bundle limit | Free plan **64 MiB uncompressed**; the docs state "There is no compressed size limit" and gzip is "shown for reference" ([limits](https://developers.cloudflare.com/workers/platform/limits/)) |
| PNG output | ~54 KB (feed), ~61 KB (story) |

Bundle contents: `worker.js` 1.5 MB, `index_bg.wasm` (resvg) 2.4 MB, `layout.wasm` (satori/yoga) 0.5 MB, 2 Poppins TTFs ~150 KB each.

**Verdict A: the flyer does NOT fit the free Workers CPU budget.** Size is fine (~4.6 MiB of 64 MiB), but rendering costs 15-35x the 10 ms limit even on the warm path, and the cold path is worse. Raster work in resvg dominates a 1080-wide canvas; shrinking the canvas is not an option because Instagram needs 1080 px. Flyers must render in the same runner as reels (or any other non-Workers process).

Caveats:
- `process.cpuUsage()` in Node is only a **proxy** for Workers CPU time (different engine/CPU, no JIT warm-up control, wasm compiled by V8 in both but not identical). The gap is large enough that the conclusion is robust, but the exact Workers number is unknown.
- Not verified: a real deploy or `wrangler dev` run. There is no Cloudflare account and I did not create one or log in. Only the dry-run bundle was produced. Satori's `standalone` entry + wasm imports bundled correctly; runtime behaviour in workerd (including startup time against the 1 s startup limit when compiling ~3 MB of wasm) is unverified.
- I did not split CPU between Satori layout and resvg rasterization.
- Paid-plan Workers (30 s CPU default) would make this trivial, but that breaks the "everything free" constraint (D6 context).

### B. Reel (FFmpeg)

Reel: 5 synthetic stills (Ken Burns zoom to 1.2x) + 1 synthetic clip, 4 s segments, 0.5 s crossfades, Poppins caption overlay per segment, 3 s end card. 1080x1920, 30 fps, H.264 High yuv420p + silent AAC stereo 44.1 kHz, `+faststart`. Duration 24.0 s, 3.5-3.9 MB.

ffprobe vs Instagram Reels spec: all PASS (MP4, H.264, AAC, 1080x1920 = 9:16, 30 fps in 23-60, size << 300 MB, 24 s within 3 s..15 min). The full ffprobe output is printed by `npm run reel` and by the CI job summary.

| Metric | Local WSL2 (16 logical CPUs) | GitHub Actions `ubuntu-latest` (4 vCPU) |
|---|---|---|
| Reel render, seconds (ffmpeg only) | 7.2, 6.9, 7.2 (and 6.7 with `-threads 4`) | 10.6, 11.9, 9.7, 7.5 (4 runs, different CPU models: Xeon 8573C, EPYC 7763, EPYC 9V74, Xeon 6975P) |
| Whole job duration | n/a | 46, 63, 46, 95 s (apt-get install of ffmpeg took 16-54 s of it) |

Queue latency (GitHub API `created_at` to `started_at`, 4 runs, 2026-11-17 ~14:00 UTC):

| | min | median | max |
|---|---|---|---|
| Job `created_at` -> `started_at` | 1 s | 1.5 s | 3 s |
| Run `created_at` -> job `started_at` | 2 s | 3 s | 4 s |
| Whole workflow run (queue + install + render + upload) | 46 s | 55 s | 95 s |

Runs: [44098731151](https://github.com/GabrielMensi/veki-companion/actions/runs/44098731151) (push), [44099007378](https://github.com/GabrielMensi/veki-companion/actions/runs/44099007378), [44099019930](https://github.com/GabrielMensi/veki-companion/actions/runs/44099019930), [44099032648](https://github.com/GabrielMensi/veki-companion/actions/runs/44099032648) (all `workflow_dispatch`). One earlier push run (44098607988) failed because `ffmpeg` is not preinstalled on `ubuntu-latest`; fixed by an apt step.

Notes:
- A 24 s reel renders in ~8-12 s on a 4 vCPU runner (about 0.4x realtime), so CI is not the bottleneck; install time and queue are small too.
- ffmpeg could be cached or run from a static binary to cut the 16-54 s apt step.

## Recommendation

1. **Flyers and reels both render in the Actions runner** (option A of docs 6.1), not in a Worker. Flyers fail the 10 ms CPU budget by more than an order of magnitude. A single job can render the flyer (Satori + resvg, ~0.2 s) and the reel (~10 s) with the same Node + ffmpeg toolchain.
2. The Worker should only enqueue: write inputs to R2, trigger the workflow, and return fast (well within 10 ms CPU). The workflow reads inputs and writes outputs through signed R2 URLs (no secrets in the public repo beyond what the dispatch carries; see risks).
3. **Local worker (option B)** stays as a fallback when Actions is unavailable, since the same scripts run in WSL in ~7 s. Oracle VM (C) and in-browser ffmpeg (D) are unnecessary given these numbers.
4. Public Actions minutes are free, so the earlier "quota exhausted" issue (private repo) does not apply here.

## Risks and open questions

- **Dispatch latency is not final.** Measured runs used `workflow_dispatch` and `push` from the feature branch. The real trigger (Worker -> GitHub API `repository_dispatch`) needs the workflow on the **default branch**, so it can only be measured after merge to `main`. Re-measure then, including the API call itself and time to first step.
- Queue latency sample is small (4 runs in a few minutes); busy periods can be slower and GitHub gives no SLA on free runners.
- Passing inputs/outputs to a public workflow: signed R2 URLs appear in public run logs/payloads unless masked. Use short-lived URLs and `::add-mask::`, or have the workflow pull via a token-less signed URL that expires in minutes. Never put real product photos in repo or artifacts (artifacts are public on public repos). Needs a design decision.
- Public-repo Actions policy: render workloads are fine, but GitHub may disable workflows on repos that look abusive; usage is tiny here.
- Scheduled workflows are disabled after 60 days of repo inactivity (not used here; `repository_dispatch` is unaffected).
- Real photos: Ken Burns on large JPEGs and real clips will cost more than these synthetic inputs; re-measure with realistic media (without committing it).
- Workers CPU for the flyer was only estimated via Node; a real Workers measurement could still be taken later if a Cloudflare account exists (expected to stay far above 10 ms).
- Fonts: the Poppins weights used (400/700) are enough for this spike; the brandbook defines more variants.
